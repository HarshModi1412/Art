# Design: First-run journey ("Set up your shop in 3 parts")

## Problem Statement
A seller who signs up for One Tap Manager lands on a home screen with twelve
module tiles, a data section and a task list. Nothing walks them from "just
signed up" to "my shop is selling". The founder's brief: ask whether they already
have a website; connect it if they do; if not, guide them through products, the
website and a payment method (Part 1), then Product Studio for the Social Media
Manager (Part 2), then stock and suppliers (Part 3). "Don't let them skip any,
but if they click on skip ask them are you sure, and if they click yes, add that
task to the task list." The bar: "even a kid should be able to use this."

## Demand Evidence
- Founder belief, not yet measured: sellers want their own website, especially
  sellers who take orders in Instagram and WhatsApp DMs. There is no named seller,
  no count and no written source yet.
- The product has no users. This is the largest open risk (see The Assignment).

## Status Quo
- DM sellers take orders in chat and are paid by UPI: the customer pays to the
  seller's UPI ID or QR and sends a screenshot.
- The storefront today accepts cash on delivery (on by default) or the seller's
  own Razorpay, Stripe or PayPal keys. Razorpay means KYC, PAN, bank proof, days
  of waiting, then pasting two keys. For a DM seller that is a wall, not a step.

## Target User & Narrowest Wedge
- The seller who takes orders in DMs and has no shop yet. Some are young and fine
  in English. Some are older and prefer Hindi or Hinglish. Both set up on a phone.
  We design for the second one.
- Wedge: in one sitting on a phone, go from nothing to a live shop link that takes
  UPI and cash on delivery, and share it.

## Constraints
- Vanilla JS single-page workspace (`Smart CafeX/smart.js`, ~12k lines),
  FastAPI backend, per-account JSON state via `user_store`.
- Existing modules stay the source of truth: Product Management, Website
  Builder, gateway settings, commerce connectors, Product Studio, Social Media
  Manager, Supply.
- Brand.md: plain words, no jargon, no dark patterns, never a cut of sales, never
  hide behind AI.
- The server has 512MB RAM. No journey step may need AI, a network call to a
  third party, or heavy server work to be counted as done.

## Premises (agreed)
1. The moment of value is "my shop link is live and I shared it". Part 1 (create
   path) ends on a live shop with Share on WhatsApp and "Copy for Instagram bio".
2. Payment in Part 1 matches how they are paid today: their UPI ID first (no KYC,
   30 seconds), with Razorpay later as an upgrade. Cash on delivery stays on.
3. Phone first, one question per screen, big buttons, guide words in English and
   Hindi.
4. (Revised after the second opinion.) The guide uses its own simple screens
   wherever the real form is dense, and saves through the same APIs into the
   same data. A step is done only when the real data says so.
5. Parts 2 and 3 are not forced on day one. They arrive as tasks after Part 1 and
   can be opened any time.

## Cross-Model Perspective
Fresh-context Claude subagent (Codex not installed):
- Steelman: "a machine that turns a DM seller into a shop owner in one sitting."
- Most revealing answer: sellers are paid by UPI screenshot today. UPI ID alone
  is not enough; the seller also needs a one-tap "mark this order paid".
- It challenged premise #4 (coach arrows over the dense real screens). The
  founder accepted, and the premise was revised.
- It recommended building Part 1 only and testing it with real sellers first. The
  founder chose the full journey (B), staged as below.

## Approaches Considered
- A) Part 1 only as simple screens; Parts 2 and 3 as coach bars on the real
  screens. Rejected: leaves Parts 2 and 3 on the dense screens.
- C) Chat-style setup. Rejected: needs AI to read free text; fragile on 512MB.

## Recommended Approach: B, the full journey on one step engine

### Delivery order (staged inside one build)
1. Step engine, API, skip-to-task and home card, with tests.
2. Part 1 create path, and UPI on the storefront, with tests.
3. Part 1 connect path.
4. Parts 2 and 3.
Each stage is working and tested before the next starts. The Assignment runs on
stage 2 as soon as it exists.

### 1. The account record
Created at registration (password and Google sign-up both), so "new" means
"signed up after this ships", not "empty":

```
user_store key "onboarding" = {
  v: 1, created_at, lang: "en"|"hi",
  path: None | "create" | "connect",
  welcomed_at, dismissed_at,
  skipped:   { step_id: iso },
  steps:     { step_id: { first_seen, done_at } },
  parts:     { "1": { opened_at, done_at }, "2": {...}, "3": {...} },
  tasks:     { tag: task_id }          # idempotency: one task per tag
}
```

Accounts with no record are existing accounts: no pop-up. Their home card asks
the welcome question the first time they open it, which sets `path`.

### 2. Steps and their "done" checks
Every check reads local stored state only (no network calls):

| Part | Path | Step | Done when (exact data) |
|---|---|---|---|
| 1 | create | `shop` | `brandname.resolve(email).ready` (a name the seller set, never a fallback), and a product type saved |
| 1 | create | `products` | 3 or more active products |
| 1 | create | `site` | site `published` with a `handle` |
| 1 | create | `payment` | commerce `upi_enabled` with a valid `upi_id`, or a gateway connected with `online_enabled` |
| 1 | connect | `connect` | any commerce connector has saved credentials, or a sales file is ready |
| 1 | connect | `catalogue` | 1 or more products in Product Management |
| 2 | both | `brand` | Studio brand `about` filled |
| 2 | both | `style` | 3 or more Studio reference photos |
| 2 | both | `photos` | at least min(3, active products) products have a photo |
| 2 | both | `instagram` | `instagram.is_connected()` (stored token) |
| 3 | both | `suppliers` | 1 or more suppliers |
| 3 | both | `stock` | at least min(3, active products) products have a stock count, and 1 or more stock items have a supplier and delivery days above 0 |

- **Prerequisites.** `site` needs `shop` done and at least 1 product. If either
  was skipped, the site screen says "Your shop needs a name and one product
  first" with a button back to that step. It never publishes an empty shop.
- **A part is finished** when each of its steps is done or skipped.
  `parts[n].done_at` is set the first time that is true.
- **Live, not frozen.** Screens always show live data. `done_at` values are
  history for the metrics. If a done step goes back (products deleted, site
  unpublished), the step shows as not done again and the home card comes back
  showing it. No part reopens and no task is created by itself.
- **`active`** is true while the account has a record, is not dismissed, and has
  any unlocked step (Part 1 always; Part 2 once Part 1 is finished; Part 3 once
  Part 2 is finished) that is neither done nor skipped.
  `finished_at` is set when all three parts are finished.
- **Numbering** comes from the path: "Step 2 of 4" on create, "Step 1 of 2" on
  connect. Skipped and done steps keep their numbers.
- **Teaching** ("how it works") lives on each part's intro and finish screens.
  It is not a step, so every step stays data-backed.

### 3. Changing the path
- `choose_path` can be called again. Connect screens have "I don't have a
  website. Make me one" and the create welcome has "I already have one".
- Switching path removes the open skip tasks for steps that are not on the new
  path. Steps on both paths keep their state.

### 4. Skip, and the task list
- "Skip for now" opens a confirm sheet: "Skip this for now?" and "It goes on your
  task list." Buttons: "No, let's do it" (primary, focused first) and "Yes, skip".
- Yes records `skipped[step]` and creates one task tagged `onboarding:<step>`.
  `tasks[tag]` makes this idempotent: skipping again reuses the open task.
- Part tasks: finishing Part 1 creates `onboarding_part:2`, finishing Part 2
  creates `onboarding_part:3`. A part task closes when its part is finished.
- A task row with an onboarding tag shows "Open", which opens the journey at that
  step or part.
- If the seller ticks or deletes an onboarding task themselves, that is their
  choice. It is not recreated. The step stays skipped and the home card still
  shows it as not done, so nothing is lost silently.
- **Reconcile is not a side effect of reading.** `progress(email)` is a pure
  read. A separate `reconcile(email)` ticks tasks whose step or part is now done
  and sets `done_at` values. It runs under a module-level lock around the read
  and write of `onboarding` and `smart_tasks`, and is called from the onboarding
  POST handler (every journey action) and from `POST /api/onboarding {action:"sync"}`,
  which the client sends when `progress().needs_sync` is true.

### 5. API and the home screen
- `GET /api/onboarding` returns `progress()`: `active`, `path`, `lang`,
  `new_account`, `current` (part and step), `parts` with steps
  (`done`, `skipped`), `needs_sync`, and the facts the screens need (shop link,
  product count, suggested web address).
- `POST /api/onboarding` actions: `choose_path`, `skip`, `open_part`,
  `seen_part_done`, `welcomed`, `set_lang`, `dismiss`, `undismiss`, `sync`.
- `/api/smart/state` carries a compact `onboarding` summary (active, current,
  counts). The home ETag fingerprint adds only the step booleans. Progress is
  memoised per account for 2 seconds so one page load computes it once.
- The home screen shows the journey card instead of the `setup_steps` card for
  every account with an onboarding record. The card has a "Hide this" control
  (`dismiss`), and "How this works" in the header brings it back. Accounts with no
  record keep the old setup card.

### 6. Screens (one question each)
Shell: a full-screen sheet on a phone, a 560px card on a laptop. Header: part
name, progress dots, English | हिंदी toggle, close. Footer: one big primary
button and a small "Skip for now". Closing the sheet (X or Escape) is "finish
later", not a skip.

- **Welcome**: "Do you already have a website?" Two big picture cards: "Yes, I
  have one" and "No, make me one".
- **Connect path**: pick a platform (Shopify, WooCommerce, Wix, Amazon, or
  "Something else: upload a sales file"). The platform's help is split into
  numbered steps above the fields. Test, connect, pull orders. Then "We found
  these products in your sales. Add them to your list?" (one tap). Imported
  products are not listed on a One Tap website. Finish (the connect value
  moment): "Your sales are in", with three facts from their own data (orders,
  top product, customers), then "Want a free One Tap shop too?" (optional), then
  Parts 2 and 3.
- **Shop**: "What is your shop called?" then "What do you sell?" (four types
  plus "in your own words"). The name is saved as the site's brand, and as the
  Studio brand name when that is empty.
- **Products**: a quick-add card with photo (optional, but asked for first:
  "Buyers want to see it"), name and price. It shows what has been added as
  thumbnails ("2 of 3"). Products are listed on the website by default.
- **Website**:
  1. Pick a look (theme cards).
  2. Your web address: suggested from the shop name, a to z, 0 to 9 and hyphens,
     3 to 30 characters, with a live availability check. If it's taken: "Taken.
     Try one of these", with two suggestions.
  3. WhatsApp number: 10-digit Indian mobile, +91 assumed; a mistake says "Enter
     10 digits".
  4. Delivery: "Free delivery" or "₹ per order".
  5. A preview of the real shop: "Looks good" or "Change the look".
  6. Publish: one big button.
  "Open the full Website Builder" is a link for anyone who wants more.
- **Payment**: "How do customers pay you?"
  - A UPI ID field ("It looks like name@okaxis"), with where to find it in GPay,
    PhonePe and Paytm.
  - Saving sets `upi_enabled` to true. It does not touch the cash on delivery
    setting, and the screen says whether cash on delivery is on.
  - "Use Razorpay instead" opens the existing gateway screen.
- **Part 1 finished** (create):
  - Site published: the live link, big, with "Share on WhatsApp" and "Copy for
    Instagram bio" (plus the two taps to paste it into the bio).
  - Site not published (skipped): "Your shop is not online yet", with "Put it
    online now". The task is already on their list.
  - Both then show "Two more parts" with one line each, and "Start Part 2" or
    "Later (on your task list)".
- **Part 2**:
  - Intro: three pictures: "You add photos", "We learn your look", "We make
    posts, you tap yes".
  - Brand: what you make, and who buys it.
  - Style photos: 3 or more.
  - Photos for products that have none.
  - Instagram: first a check screen: "Your Instagram must be a Business or
    Creator account. It is free." Then how to switch (Settings, Account type,
    Switch to professional). Then Connect (the existing flow). If connecting
    fails, it says why in plain words and offers Skip.
  - Finish: "Your Social Media Manager is ready". "Plan my first week" opens the
    Social Media Manager, whose planning uses AI and says so. It counts toward
    AI uses, and when AI is off on the server it says that plainly. The journey
    step itself never needs AI.
- **Part 3**:
  - Intro: three pictures: "Tell us who you buy from", "We watch what sells",
    "We warn you before it runs out".
  - Supplier: name, WhatsApp, and "How many days to deliver?". Delivery days are
    saved on each stock item's `lead_time_days` (the field Supply's reorder
    reads) and shown against the supplier.
  - Stock: "How many do you have?" for up to 20 products (top sellers first when
    there are sales), with a search box for the rest. Each answer sets the
    product's stock and creates or updates the matching stock item, with the
    supplier and delivery days.
  - Finish: their own example from Supply's real rule (reorder when stock lasts
    less than delivery days plus 20%): "Kurta sells about 2 a day." "Supplier
    takes 7 days." "We will warn you at 17." (2 × 7 = 14, plus a little extra
    for safety.) It is labelled as an example when there are no sales yet.

Already-done steps are passed silently with a tick. A returning seller lands on
the first thing still missing.

### 7. UPI on the storefront (new capability)
- The site's commerce settings gain `upi_id` (validated as `name@bank`: 2 to 256
  of letters, digits, dots, hyphens and underscores, then @, then 2 to 64
  letters and digits) and `upi_enabled`.
- Offered only when the store currency is INR. Order at checkout: UPI (selected
  by default when on), then cash on delivery, then an online gateway if
  connected.
- After the order is placed, the shopper sees the amount and the order number
  big. The seller's UPI ID has a Copy button: "Pay to this UPI ID". "Open UPI
  app" is secondary, using `upi://pay?pa=&pn=&am=&cu=INR&tn=<order no>`. Then
  "Send payment screenshot on WhatsApp" opens a chat to the seller's number with
  the order number filled in.
- **Unverified and must be tested:** some UPI apps restrict links with a preset
  amount to personal (non-merchant) IDs. So copying the ID is the main path and
  the link is only a convenience. The Assignment includes testing the link on
  GPay, PhonePe and Paytm.
- The order is created at once with payment `upi` and payment status "to check".
  Stock goes down as it does for a cash on delivery order. The shopper can never
  mark it paid.
- In Orders, a UPI order shows "Payment to check" and how long it has waited.
  Two buttons: "Money received" (marks it paid) and "Not received" (cancels the
  order through the existing cancel, which puts stock back). Nothing expires in
  v1, and the shopper is not notified in v1.
- No QR image in v1: it would need a new dependency.
- Shopper-facing UPI words are English in v1, like the rest of the storefront.

### 8. Words and language
- Every journey string exists in English and Hindi (Devanagari) in one client
  dictionary. Hinglish is noted as a possible later option.
- Choice: saved in the `onboarding` record (`set_lang`). Default is English, and
  the toggle is on every screen. Linked screens (the full Website Builder, the
  Razorpay screen, Product Management) stay English.
- Sentences stay under 12 words, with no jargon (no SKU, gateway, handle,
  inventory, API). Each step says what the seller gets.

### 9. Photos
- Photos are resized in the browser before upload: longest side 1600px, JPEG at
  0.85. Upload uses the existing `/api/site/image` with its progress bar.
- A failure keeps the chosen photo and shows "Try again".
- Journey uploads are the seller's own photos. They trigger no AI and no AI
  labelling.

### 10. Quality bar
- 44px targets, visible focus, focus moves to each new screen's heading,
  Escape is "finish later", works at 375px, dark mode, reduced motion.
- Every save shows its result. A failure says what happened and keeps what the
  seller typed.

## Open Questions
- Should a "to check" UPI order send the shopper a confirmation when it is marked
  paid (email or WhatsApp)? Deferred until sellers use it.
- Hinglish as a third language option? Decide after watching Hindi-preferring
  sellers.

## Success Criteria
- A new seller on a 375px phone reaches a published shop with UPI on, in one
  sitting, without opening any module tile.
- No skip is lost silently. Every skip is a task (one per step), and each task
  closes itself when its step is done.
- A step is never shown done unless the real data says so, and a step that
  regresses shows as not done (covered by tests).
- Measured from the record: time from `created_at` to `parts.1.done_at`, and the
  last `first_seen` step for accounts that stop.

## Dependencies
- Existing APIs: products, site state/save/publish, gateway, commerce connect,
  studio brand/refs, Instagram connect, supply suppliers/items, tasks, orders.
- New: onboarding module and API, UPI commerce fields, storefront UPI checkout,
  order "Money received" and "Not received".

### R2-1 — consistency

**Problem**

> The document gives two rules for existing accounts. Section 1 says accounts with no record get a home card that asks the welcome question the first time they open it, which sets `path`. Section 5 says the journey card replaces `setup_steps` only for accounts with an onboarding record, and accounts with no record keep the old setup card. Under section 5, an existing account never sees the journey card, so it can never answer the welcome question. Nothing says when a record is created for these accounts, and `choose_path` and `set_lang` need one.

**Remedy**

> Pick one rule. Either existing accounts never enter the journey, which means deleting the section 1 sentence, or their home card offers the journey and a record (without `welcomed_at`, and with no pop-up) is created the first time they open it. Make section 5 match whichever is chosen.

### R2-2 — clarity

**Problem**

> The home card is undefined once `active` is false. `active` becomes false when every unlocked step is done or skipped. Section 4, however, promises that a skipped step whose task the seller deleted is still shown as not done on the home card. The doc also still doesn't say whether `setup_steps` returns for record-holding accounts after the journey ends or is hidden. It also doesn't say which header holds 'How this works', the control that undoes `dismiss`.

**Remedy**

> State what the home card shows when `active` is false: hidden, an 'all done' state, or a list of the skipped steps that are still not done. Keep section 4's promise consistent with that choice. Say whether `setup_steps` ever returns, and name where 'How this works' lives.

### R2-3 — consistency

**Problem**

> Premise 5 says Parts 2 and 3 'can be opened any time'. The `active` rule instead unlocks Part 3 only once Part 2 is finished, and the `onboarding_part:3` task is created only when Part 2 finishes. A seller who does not use Instagram has to go through four skip-confirm sheets in Part 2 before stock and suppliers become reachable. The connect finish screen also says 'then Parts 2 and 3', which suggests both are offered.

**Remedy**

> Decide whether the parts are locked in order. If Part 3 can be opened on its own, change the unlock rule in `active` and say when the Part 3 task is created. If the parts are locked, reword Premise 5 and the connect finish screen to match.

### R2-4 — consistency

**Problem**

> The `payment` done check is `upi_enabled` plus a valid `upi_id`, but section 7 offers UPI at checkout only when the store currency is INR. The journey never sets or checks the currency. A store whose currency defaults to something other than INR would show the payment step as done while shoppers never see UPI. That fails the success criterion 'a published shop with UPI on' and Premise 4.

**Remedy**

> Either have the Payment (or Website) step set or confirm INR as the currency, or add 'currency is INR' to the `payment` done check. Say what the Payment screen shows when the currency is not INR.

### R2-5 — clarity

**Problem**

> The connect-path offer 'Want a free One Tap shop too?' has no defined behavior. The doc does not say whether 'yes' calls `choose_path` with `create`, which section 3 says would remove open skip tasks for the connect steps. It also doesn't say which create steps the seller then goes through, or whether imported products (which are 'not listed on a One Tap website') become listed.

**Remedy**

> Specify what 'yes' does: whether it switches the path or adds the create steps alongside the connect ones, which steps are shown, how they are numbered, and whether imported products get listed on the new site.

### R2-6 — clarity

**Problem**

> Path switching covers skip tasks only. The doc doesn't say what happens to `parts.1.done_at`, the `onboarding_part:2` task, or Part 2 and 3 unlocking when a seller switches path after Part 1 was already finished on the old path. It also doesn't say whether the new path's Part 1 must be finished again.

**Remedy**

> State the effect of a path switch on part completion, part tasks and unlocked parts. For example: Part 1 is recomputed from the new path's steps, while `done_at` stays as history.

### R2-7 — clarity

**Problem**

> The `photos` and `stock` checks use min(3, active products). With 0 active products that minimum is 0, so `photos` is done with no action from the seller, and 'already-done steps are passed silently with a tick'. 'Active product' is also undefined for connect-path imports, which are 'not listed on a One Tap website'. If imports don't count as active, connect sellers get vacuous `photos` and `stock` checks.

**Remedy**

> Define 'active product' and whether imported products count. State the behavior when there are 0 qualifying products, for example the step is locked behind having a product, or requires at least 1.

### R2-8 — clarity

**Problem**

> The `shop` done check requires 'a product type saved', but the doc never names the field or store that holds the answer to 'What do you sell?'. It names only the brand name targets: the site's brand, and the Studio brand name when that is empty.

**Remedy**

> Name the exact field the product type is saved to, including the 'in your own words' answer, and the module that owns it.

### R2-9 — completeness

**Problem**

> `reconcile()` runs only on onboarding POST actions and on the `sync` the client sends after reading `progress().needs_sync`. The `/api/smart/state` summary is listed as active, current and counts, with no `needs_sync`. A step finished inside a real module, such as adding products in Product Management or connecting Instagram from its own screen, therefore does not close its skip task or set `done_at` until the seller opens the journey. That undercuts the success criterion 'each task closes itself when its step is done' and skews the `done_at`-based metrics.

**Remedy**

> Say which client surfaces trigger `sync`, for example by adding `needs_sync` to the state summary and having home send `sync`, or call `reconcile` from the relevant save handlers. Note that `done_at` records when a step was observed done, not when the data changed.

### R2-10 — completeness

**Problem**

> The web address is suggested from the shop name using a to z, 0 to 9 and hyphens. The design targets Hindi-preferring sellers, whose shop name may be in Devanagari. For such a name the doc defines no suggestion: no transliteration and no fallback.

**Remedy**

> Define the suggestion for a non-Latin shop name: transliterate it, or leave the field empty with a plain example and a Hindi hint about the allowed letters.

### R2-11 — completeness

**Problem**

> The UPI checkout's 'Send payment screenshot on WhatsApp' needs the seller's WhatsApp number. That number is collected only in the journey's Website step. A shop published through the full Website Builder, or before this feature existed, may have UPI on but no number.

**Remedy**

> State that the screenshot button is hidden when no seller number is saved. Alternatively, ask for the number on the Payment screen when it is missing.

### R2-12 — feasibility

**Problem**

> `reconcile` holds a module-level lock around its read and write of `onboarding` and `smart_tasks`. Other writers of `smart_tasks`, such as the task list's own tick, delete and create handlers, don't take that lock, so a seller's tick that lands during a reconcile can be lost. A module-level lock also protects nothing if the server runs more than one worker process.

**Remedy**

> Guard the updates with the same per-account lock or atomic update that `user_store` and the task handlers use. Otherwise, state that the app runs one worker and that every `smart_tasks` writer takes this lock.

### R2-13 — feasibility

**Problem**

> Progress is memoised per account for 2 seconds. When a seller saves a step and the guide calls progress again to move on, it can get the cached result and show the step just saved as not done. That breaks 'every save shows its result'.

**Remedy**

> Invalidate the memo on every onboarding POST and on the saves the journey makes, or bypass it for `GET /api/onboarding` and use it only for `/api/smart/state`.

### R2-14 — feasibility

**Problem**

> Section 9 sends every journey upload through `/api/site/image`. But the `style` check reads Studio reference photos, and the `photos` check reads each product's photo, and those are separate stores. Uploads that land only in site images would never satisfy those checks. The Part 2 intro promises 'We learn your look', while section 9 says journey uploads trigger no AI, so it is unclear when or how the look is learned.

**Remedy**

> Name the upload endpoint and destination for each step (quick-add product photo, style photos, product photos) so each done check sees the result. Say whether Studio analyses the style photos later, and whether that uses AI.

### R2-15 — scope

**Problem**

> Delivery is now staged, but it is still 'staged inside one build'. Stages 3 and 4 (the connect path and Parts 2 and 3) start as soon as the previous stage is tested, not after The Assignment's observations on stage 2 are in. The remaining build can therefore still run ahead of the evidence.

**Remedy**

> Add an explicit checkpoint after stage 2: record the Assignment results, and let them change or reorder stages 3 and 4 before those are built.
